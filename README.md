# 🎙️ Стенограф

[![Tests](https://github.com/seregaslime/stenograf/actions/workflows/tests.yml/badge.svg)](https://github.com/seregaslime/stenograf/actions/workflows/tests.yml)
[![Build installers](https://github.com/seregaslime/stenograf/actions/workflows/build.yml/badge.svg)](https://github.com/seregaslime/stenograf/actions/workflows/build.yml)

Десктоп-приложение для протоколирования встреч: превращает речь с **микрофона**
и **системного звука** (корпоративный звонок, вебинар) в текстовый чат в реальном
времени, различает голоса участников и по окончании встречи составляет протокол
с помощью **локальной LLM** — данные не покидают машину или контур организации.

## Возможности

- **Живая транскрипция** — реплики появляются в чате через 1–3 секунды после фразы
  (silero-VAD + сменный ASR-движок). Движок и модель переключаются прямо в
  настройках без перезапуска: **GigaAM v3** (Сбер, лучшее качество для русского,
  текст сразу с пунктуацией), whisper на CPU (faster-whisper) или на GPU
  (mlx-whisper, Metal на Apple Silicon).
- **Один поток из двух каналов** — микрофон и системный звук (звонок) склеиваются
  на сервере в единую шкалу времени и распознаются одним проходом; эхо из колонок
  не создаёт дублей, потому что копия голоса совпадает по времени с оригиналом.
- **Диаризация с памятью** — «отпечаток» голоса (ECAPA-TDNN) сверяется с глобальной
  базой спикеров: человек узнаётся и на следующих встречах. Профиль владельца («Вы»)
  обучается автоматически по голосу, доминирующему в микрофоне, — поэтому за одним
  микрофоном могут сидеть несколько человек, их разделит по тембру. Ошибки чинятся
  вручную: на вкладке «Спикеры» у каждого профиля видны «звучания» голоса — их
  можно прослушать, удалить неудачное или объединить два профиля, — реплики
  переписываются во всех встречах.
- **Протокол от LLM** — по окончании встречи локальная Ollama (qwen3:4b) составляет
  итог: краткое описание → ключевые темы → решения → задачи. Экспорт в `.md` / `.txt`.
  Вместо локальной модели можно подключить **внешний API** (адрес, ключ и модели
  вводятся в настройках; ключ хранится на сервере и на клиент не отдаётся) — по
  умолчанию всё остаётся локальным. Пока поддерживается только **Groq**: он
  сообщает размер контекста каждой модели, и приложение само прячет из выбора те,
  что не потянут наши промпты.
- **Подсказки ИИ во время встречи** — модель следит за разговором и вмешивается
  только когда есть что сказать: отвечает на прозвучавший без ответа вопрос,
  расшифровывает термин, замечает риск или задачу без срока. **Имеет право
  промолчать** — на болтовне ни о чём подсказок не будет, и это норма. Без
  повторов, включаются/выключаются на лету, есть кнопка «подсказать сейчас»
  (она отвечает всегда).
- **Тип встречи** — планёрка, собеседование (подсказки на стороне соискателя)
  или переговоры: меняет и фокус подсказок, и разделы протокола.
- **Клиент-серверная архитектура** — клиент лёгкий (Electron), все модели на сервере.
  Сервер запускается локально **или** на сервере организации — тогда сотрудникам
  не нужно «тянуть» модели на свои машины.

## Архитектура

```
Клиент (Electron + React + TS)          Сервер (Python + FastAPI)
┌─────────────────────────┐             ┌────────────────────────────────────┐
│ микрофон  ─┐            │  WebSocket  │ микшер каналов → денойз* → VAD →   │
│ система   ─┴→ PCM16 16k │ ──────────► │ → ASR (GigaAM / whisper) →         │
│ (loopback / BlackHole)  │ ◄────────── │ → ECAPA-эмбеддинг → база голосов → │
│ чат, спикеры, история   │   события   │ → SQLite → события клиенту         │
└─────────────────────────┘             │ Ollama: протокол и подсказки       │
                                        └────────────────────────────────────┘
```

Этапы конвейера обособлены (`audio/mixer.py`, `audio/denoise.py`, `audio/vad.py`,
`asr/`, `diarization/`) и заменяются независимо. Микшер помнит энергию каждого
канала: по ней диаризация понимает, из комнаты голос (микрофон) или из звонка.
*денойз — заготовка (по умолчанию `off`): современные ASR обучены на шумной
речи, включать чистку стоит только по результатам замеров.

## Установка клиента (готовые сборки)

Собираются командами `npm run dist:mac` и `npm run dist:win` в папке `client`,
а также автоматически в GitHub Actions (workflow «Build installers»). Каждая
платформа даёт два варианта:

| | macOS | Windows |
|---|---|---|
| **без установки** | `.zip` — распаковать и запустить | `-portable-x64.exe` — просто запустить |
| с установкой | `.dmg` | `.exe` (NSIS) |

Портативный вариант нужен, чтобы посмотреть приложение, ничего не устанавливая
и не собирая: скачал один файл — запустил. Настройки он всё равно хранит в
профиле пользователя, поэтому адрес сервера переживает перезапуск.

Готовые файлы лежат в [релизах](https://github.com/seregaslime/stenograf/releases)
— туда их выкладывает CI, когда на коммит поставлен тег `v*`. Версия в теге
должна совпадать с `version` в `client/package.json` (иначе прогон упадёт с
объяснением): имена файлов берут версию оттуда, и релиз `v0.3.0` с файлами
`Stenograf-0.2.0-*` выглядел бы как выложенная не та сборка. Артефакты
отдельных прогонов Actions тоже остаются, но живут 90 дней и видны только тем,
кто вошёл в GitHub.

Сборки не подписаны сертификатом разработчика, поэтому при первом запуске:
- **macOS**: правый клик по приложению → «Открыть» (или снять карантин:
  `xattr -cr /Applications/Стенограф.app`). Приложение заново попросит доступ
  к микрофону и «Записи экрана и звука системы» — это нормально, у
  упакованного приложения свои разрешения.
- **Windows**: в предупреждении SmartScreen — «Подробнее» → «Выполнить в любом
  случае».

Клиенту нужен работающий сервер (локально или адрес сервера организации в
Настройках).

## Быстрый старт (локально, macOS/Linux)

Требования: Python 3.11+ (или [uv](https://docs.astral.sh/uv/)), Node.js 20+,
[Ollama](https://ollama.com).

```bash
# LLM-модели (один раз)
ollama pull qwen3:4b    # протоколы встреч
ollama pull qwen3:1.7b  # подсказки в реальном времени (быстрая)

# Всё остальное — одной командой (Ollama + сервер + приложение):
./start.sh
```

При первом запуске сервер сам создаст окружение и скачает модели распознавания.
По частям, если нужно:

```bash
./server/run.sh         # только сервер (окружение создаётся автоматически)
cd client && npm install && npm run dev:app   # приложение в dev-режиме (Vite + Electron)
# npm run dev — только браузерная версия на http://localhost:5173, без Electron
```

При первом запуске сервер скачает модели: GigaAM (~530 МБ), ECAPA (~80 МБ),
а при переключении движка — whisper (до ~900 МБ). Всё складывается в
`server/data/models`; первая встреча может стартовать с задержкой.

## Системный звук

Режим «Автоматически» (по умолчанию) захватывает звук системы **без драйверов**
через [electron-audio-loopback](https://github.com/alectrocute/electron-audio-loopback)
(ScreenCaptureKit на macOS, WASAPI loopback на Windows):

| ОС | Как работает |
|---|---|
| **Windows** | Из коробки. |
| **macOS 13+** | При первом запуске разрешите приложению «Запись экрана и звука системы» (Системные настройки → Конфиденциальность) и перезапустите его. macOS Sequoia периодически просит подтвердить разрешение повторно — это системное поведение. |
| **macOS ≤ 12 / браузер** | Запасной путь: виртуальный аудиокабель [BlackHole](https://github.com/ExistentialAudio/BlackHole) (`brew install blackhole-2ch`), затем в «Настройка Audio-MIDI» — «Устройство с несколькими выходами» (динамики + BlackHole) как системный выход, а BlackHole выбрать источником в приложении. |

Важно: Electron должен оставаться на ветке 35.x — в Electron 40+ регрессия,
loopback-аудио на macOS возвращает тишину
([electron#49607](https://github.com/electron/electron/issues/49607)).

Совет: в наушниках качество диаризации выше — голоса собеседников не попадают
в микрофон через комнату и не смешиваются с вашим голосом (дублей реплик микшер
не допускает в любом случае, но «комнатная» копия голоса портит тембр).

## Сервер организации

Сервер поднимается на общей машине так же, как локально (`server/run.sh`,
`HOST=0.0.0.0`), рядом нужна Ollama. В клиенте: **Настройки → Адрес сервера** →
`http://<хост>:8765` — звук стримится по WebSocket, модели живут на сервере.

### Доступ по токену

Пока на сервере не заведён ни один человек, он пускает всех без токена — так
работает личный запуск на ноутбуке. Как только заведён первый, токен становится
обязательным для всех запросов:

```bash
python -m app.users add "Сергей"      # напечатает токен — он показывается один раз
python -m app.users list
python -m app.users remove 2
```

В контейнере — `docker compose exec server python -m app.users add "Сергей"`.

У каждого заведённого человека своё приложение: свои встречи, своя библиотека
голосов и свой профиль «Вы». Пересечений нет — один и тот же собеседник у двух
пользователей это два независимых профиля. Иначе «Вы» (владелец микрофона) был
бы общим на двоих, а на нём висит скидка к порогу узнавания: голоса разных людей
слились бы в один профиль.

Токен вводится в клиенте: **Настройки → Токен доступа**. Оттуда он уходит
заголовком `Authorization` в обычных запросах и первым кадром `auth` в живой
встрече — заголовки браузерному WebSocket задать нельзя, а в адресе токен попал
бы в журналы сервера.

В базе лежит только хеш токена, восстановить нельзя — потерялся, выдайте новый.
Удаление последнего человека снова открывает сервер без токена, команда об этом
предупреждает.

Открытым остаётся только `/api/health`, и без токена он отвечает лишь «жив»: по
нему видно, поднялся ли сервер, до того как введён токен. `CORS` при этом
сервер не защищает — он защищает пользователя браузера от чужих сайтов; от
запроса curl-ом спасает именно токен.

### В контейнерах (Docker)

`docker-compose.yml` поднимает сервер + Ollama:

```bash
docker compose up -d --build
docker compose exec ollama ollama pull qwen3:4b     # протоколы (один раз)
docker compose exec ollama ollama pull qwen3:1.7b   # подсказки (один раз)
```

Модели ASR (GigaAM/whisper/ECAPA) скачиваются при первом запуске в том
`stenograf-data`. Клиент указывает на `http://<хост>:8765`. Внешний LLM-API вместо
Ollama включается переменными `STENOGRAF_LLM_*` в `docker-compose.yml` (ключ в образ
не попадает). `torch` ставится CPU-сборкой, `mlx` пропускается сам (только macOS).

**Видеокарта в этом образе не используется.** `torch` ставится CPU-сборкой
([server/Dockerfile](server/Dockerfile)) — без CUDA образ в разы меньше, но и
`STENOGRAF_ASR_DEVICE=cuda` внутри контейнера ничего не даст: карты для torch
там просто нет. Чтобы считать на видеокарте, запускайте сервер напрямую
(`server/run.sh`) — при установке в обычное окружение torch сам подтянет сборку
с CUDA. Отдельного GPU-образа пока нет.

### Обновление сервера

Образ собирается в CI и публикуется по мержу в `main`, поэтому на машине его
собирать не надо — только забрать:

```bash
ssh root@<хост> 'cd /opt/stenograf && sh deploy/update.sh'
```

Скрипт снимает копию базы (миграции побегут при старте нового контейнера, и
откат образа схему обратно не откатит), тянет `latest`, перезапускает сервер,
дожидается ответа `/api/health` и убирает висячие слои. Логин в реестр не
нужен: пакет публичный, как и сам репозиторий. Собирать на самой
машине нельзя: там меньше двух гигабайт свободной памяти, а установка torch их
съедает — неудачная сборка оставит сервер лежать.

**Откат.** CI публикует второй тег с git-sha каждого мержа. Чтобы вернуться на
предыдущую версию, пропишите этот тег вместо `latest` в
`docker-compose.override.yml` и поднимите сервис заново. Если после отката
данные выглядят странно — восстановите копию базы, снятую скриптом
(`/data/stenograf.backup-*.db` в томе).

**Какая версия сейчас стоит** видно в `/api/health` и в строке состояния
приложения: там короткий git-sha, а не постоянная «0.1.0», как было раньше.

## Регрессионный прогон

Тесты проверяют логику, но не качество: после правки VAD, ASR или диаризации всё
зелёное, а распознаёт хуже — и заметить это можно только на слух и поздно.

```bash
cd server && .venv/bin/python scripts/regress.py
```

Считает два числа на эталонном наборе и сравнивает с `baseline.json`: долю
ошибок в словах (WER) и ошибки диаризации — раздвоения и склейки. Стало хуже
допуска — выход с кодом 1.

Набор синтезирован системным голосом macOS (`scripts/make_regress_fixtures.py`)
и лежит в репозитории: расшифровка известна заранее, а живые записи участников
встреч в публичный репозиторий класть нельзя.

Модели живут в контейнере, поэтому на практике:

```bash
docker compose cp server/scripts/regress.py server:/tmp/regress.py
docker compose cp server/tests/fixtures server:/tmp/fixtures
docker compose exec -e PYTHONPATH=/srv server python /tmp/regress.py --fixtures /tmp/fixtures/regress
```

Руками этот прогон запускать больше не обязательно: его же делает CI на каждый
пул-реквест (job «Медленные уровни и эталон голоса»), и числа видны в сводке
запуска, а не только в логах.

## Поиск по прошлым встречам

Договорённости растворяются: через месяц никто не помнит, на какой встрече
решили перенести сроки. **История встреч → поле поиска** — вопрос своими
словами, в ответ цитаты со ссылкой на разговор и минуту.

Поиск идёт по смыслу, а не по словам: «что решили по срокам» находит разговор,
где говорили «двигаем сдачу на следующий месяц». Каждый кусок разговора
превращается в вектор моделью эмбеддингов, вопрос — тоже, и берутся ближайшие.
Это ровно то, что уже делает диаризация с голосами, только сравниваются не
тембры, а смыслы — поэтому и отдельной векторной СУБД здесь нет: на живом
архиве это матрица в единицы мегабайт, полный перебор занимает миллисекунды.

Нужна модель эмбеддингов в Ollama (один раз):

```bash
ollama pull bge-m3
```

Индексация ленивая: первый поиск после новой встречи считает её куски сам,
поэтому идёт дольше обычного. Качество поиска меряется на эталонном наборе —
`scripts/eval_search.py` (см. «Регрессионный прогон» рядом).

Над цитатами появляется **ответ модели**, собранный по найденному. Он приходит
вторым запросом: поиск отвечает за доли секунды, модель — за секунды, и цитаты
успевают появиться раньше. Модель не помнит встреч и отвечает только по
показанным ей фрагментам: не нашлось — скажет «в записях встреч этого нет», а
не достроит правдоподобный ответ. Поэтому цитаты и остаются на экране рядом с
ответом — по ним ответ проверяется за пару секунд.

По умолчанию отвечает модель протокола: ответ по пяти фрагментам из разных
встреч ближе к резюме, чем к подсказке на лету. В **Настройках** это
переключается на модель подсказок — она заметно быстрее, а на этих промптах
отвечает не хуже (замер на M3 с Metal: `qwen3:4b` — 36 секунд, `qwen3:1.7b` —
13 секунд, оба ответили верно).

> ⚠️ **Ollama в Docker на macOS работает без видеокарты** — контейнеру Metal
> недоступен. Замер на 8 ядрах: `qwen3:4b` выдаёт 5.6 токенов в секунду, и
> ответ по архиву занимает минуты. Для локальных ответов держите Ollama на
> самом хосте (там Metal) и укажите приложению её адрес:
> `http://host.docker.internal:11434` в **Настройках → Адрес Ollama**.
> Через внешний API ответ приходит за секунды и памяти не требует.

## Конфигурация сервера

Все параметры — переменные окружения с префиксом `STENOGRAF_` (или `server/.env`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `STENOGRAF_ASR_ENGINE` | `gigaam` | Движок: `gigaam` / `faster_whisper` (CPU) / `mlx` (GPU, Apple Silicon) |
| `STENOGRAF_ASR_MODEL` | `v3_e2e_rnnt` | whisper: `tiny`/`base`/`small`; gigaam: `v3_e2e_rnnt`/`v3_e2e_ctc` |
| `STENOGRAF_ASR_DEVICE` | `auto` | Где считать: `auto` (видеокарта NVIDIA, иначе процессор), `cuda`, `mps`, `cpu` |
| `STENOGRAF_ASR_COMPUTE_TYPE` | `auto` | Точность faster-whisper: `auto` (`float16` на видеокарте, `int8` на процессоре) |
| `STENOGRAF_ASR_LANGUAGE` | `ru` | Язык распознавания whisper (`auto` — автоопределение); GigaAM всегда русский |
| `STENOGRAF_SPEAKER_MATCH_THRESHOLD` | `0.35` | Порог «тот же голос» (косинусная близость, см. `scripts/eval_voices.py`) |
| `STENOGRAF_SPEAKER_CHANNEL_DOMINANCE` | `2.0` | Во сколько раз канал должен быть громче, чтобы считаться источником голоса |
| `STENOGRAF_DENOISE` | `off` | Этап чистки шума в конвейере (заготовка) |
| `STENOGRAF_VERSION` | `dev` | Версия кода в `/api/health`; ставится при сборке образа из git-sha |
| `STENOGRAF_CORS_ORIGINS` | `null` | Кому браузер разрешит читать ответы, вдобавок к локальным адресам. `null` — собранное приложение (грузится с `file://`) |
| `STENOGRAF_SEARCH_CHUNK_CHARS` | `600` | Сколько символов набирать в кусок разговора перед подсчётом вектора |
| `STENOGRAF_SEARCH_TOP_K` | `5` | Сколько кусков отдавать на один запрос |
| `STENOGRAF_DATA_DIR` | `server/data` | БД, модели, аудио «звучаний» голоса, записи |

Движок ASR, выбранный в настройках приложения, сохраняется в `data/asr.json` и
имеет приоритет над переменными окружения.

**Настроек модели здесь нет** — ни адреса, ни ключа, ни имён моделей: с
05.09.2026 всё это живёт в приложении, у каждого своё (см. «Модель — у
пользователя»). Старые строки `STENOGRAF_LLM_*` и `STENOGRAF_OLLAMA_URL` сервер
молча пропускает, чтобы не упасть при обновлении, но не читает — их стоит
удалить, особенно ключ.

## Выбор модели распознавания

Замер на синтезированной русской речи с терминами и именами
(`scripts/bench_asr.py`, MacBook Air M3, 8 ГБ; WER — доля ошибочных слов,
×RT — во сколько раз быстрее реального времени):

| Модель | WER | Скорость | RAM |
|---|---|---|---|
| **GigaAM v3 rnnt** (CPU) — по умолчанию | **1.2%** | 14×RT | ~1.1 ГБ |
| GigaAM v3 ctc (CPU) | 4.9% | 13×RT | ~1.2 ГБ |
| faster-whisper small (CPU) | 9.8% | 2–3×RT | ~530 МБ |
| mlx small q4 (GPU) | 13.4% | 10–14×RT | ~340 МБ |
| mlx base q4 (GPU) | 19.5% | 27×RT | ~240 МБ |
| faster-whisper base (CPU) | 20.7% | 6–10×RT | ~290 МБ |
| faster-whisper tiny (CPU) | 28.0% | 15–20×RT | ~280 МБ |
| mlx tiny q4 (GPU) | 35.4% | 42×RT | ~100 МБ |

Синтетическая речь чище живой, поэтому абсолютные числа занижены, но
соотношение моделей сохраняется. Практический вывод: **GigaAM v3 rnnt** —
одновременно самая точная (одна ошибка на 82 слова, сразу с пунктуацией)
и одна из самых быстрых, поэтому она и стоит по умолчанию. Whisper остаётся
запасным вариантом: `small` — если не хватает памяти (GigaAM тяжелее на
~600 МБ), `mlx` — если важно разгрузить CPU, мультиязычность — только whisper
(GigaAM распознаёт русский).

## Тесты

Уровни: юнит → компонентные (API-слой) → интеграционные → e2e, плюс нагрузочный;
на клиенте — Vitest.

Два документа, оба **генерируются из кода и артефактов прогона**, а не пишутся
руками:

- **[TEST_REPORT.md](TEST_REPORT.md)** — сколько тестов, что прошло/упало,
  покрытие строк и ветвей, вклад каждого уровня.
- **[TESTS.md](TESTS.md)** — каталог: каждый тест, где лежит и что проверяет.

```bash
cd server
uv pip install --python .venv/bin/python -r requirements-dev.txt   # один раз (pytest, pytest-cov)

# Отчёт целиком: гоняет уровни, считает покрытие, перезаписывает TEST_REPORT.md
.venv/bin/python scripts/test_report.py          # быстрые уровни (секунды)
.venv/bin/python scripts/test_report.py --all    # + integration/e2e/load (минуты)
.venv/bin/python scripts/test_inventory.py       # пересобрать каталог TESTS.md

# Отдельные уровни вручную
.venv/bin/python -m pytest                  # быстрый набор
.venv/bin/python -m pytest -m integration   # реальная ECAPA на синтезе голосов macOS
.venv/bin/python -m pytest -m e2e           # встречи целиком: живой сервер + WebSocket
.venv/bin/python -m pytest -m load          # дымовой нагрузочный (2 параллельные встречи)
.venv/bin/python scripts/loadtest.py --meetings 5 --seconds 30   # полноценная нагрузка

cd ../client && npm run test                # юнит-тесты клиента (Vitest + jsdom)
```

Построчный отчёт о покрытии после прогона: `server/reports/htmlcov/index.html` —
видно, какие именно строки и ветки не покрыты.

> ⚠️ Уровню **e2e нужно ~2 ГБ свободной памяти**: он поднимает свой сервер и
> грузит GigaAM. На 8 ГБ перед `--all` остановите Docker (`docker compose down`)
> и тяжёлые приложения — иначе сервер не успеет подняться и все e2e упадут с
> `TimeoutError: сервер не поднял ASR`. Это нехватка памяти, а не поломка кода.

**Прогон в Docker** (доказательство, что числа воспроизводятся на чистой
Linux-машине, а не только на макбуке разработчика):

```bash
docker build --target test -t stenograf-test ./server && docker run --rm stenograf-test
```

Те же тесты гоняет CI — [.github/workflows/tests.yml](.github/workflows/tests.yml);
HTML-покрытие и JUnit XML можно скачать из вкладки Actions.

Быстрый набор идёт на Linux, а `integration`, `e2e` и регрессионный прогон — на
macOS-раннере: оба медленных уровня синтезируют голоса командой `say`, и на
Linux они бы просто скипнулись, оставив зелёный прогон, в котором ничего не
выполнилось. Веса моделей (~500 МБ) кешируются между запусками, поэтому прогон
укладывается в три минуты.

Ручной чек-лист перед показом (реальный микрофон, звонки, железо) — [TESTING.md](TESTING.md).

### Нагрузочные прогоны

Нагрузка подаётся **на контейнер**, а не на рабочую машину: контейнер играет
роль сервера организации с известным лимитом ресурсов (`mem_limit: 3g` в
[docker-compose.yml](docker-compose.yml)), и его можно валить, не трогая ноутбук.

```bash
docker compose up -d --no-deps server
cd server

# Параллельные встречи: рампа, пока сервер не начнёт деградировать
.venv/bin/python scripts/loadtest.py --url http://127.0.0.1:8765 \
    --container practika-server-1 --ramp --report reports/loadtest.md

# Обстрел REST-эндпоинтов: сколько одновременных запросов держит
.venv/bin/python scripts/spamtest.py --url http://127.0.0.1:8765 \
    --ramp --report reports/spamtest.md
```

`--container` включает замер памяти через `docker stats` и ловит падение
контейнера по `docker inspect` (рост `RestartCount`, флаг `OOMKilled`). Рампа
останавливается, когда появляются ошибки, контейнер перезапустился или p95
задержки превысил порог. Оба скрипта пишут markdown-отчёт с таблицей ступеней.

Важно про два режима подачи аудио:

- **по умолчанию** кадры летят в 20 раз быстрее живого клиента — это меряет
  пропускную способность и глубину очереди («сколько встреч можно свалить разом»);
- **`--realtime`** шлёт аудио как настоящий клиент и меряет то, что нужно для
  сайзинга: сколько ЖИВЫХ встреч сервер тянет, не отставая.

Числа сильно разные: пачкой сервер переваривает больше сотни встреч, а живых
держит 3–4.

Всё в одном месте — [**LOAD_REPORT.md**](LOAD_REPORT.md): что мерили, что
получилось, какие дефекты нашли и **какое железо нужно серверу** (ядра, память,
диск → сколько человек потянет и с какой задержкой).

Отдельно есть `scripts/bench_registry.py` — рост времени опознания голоса при
увеличении библиотеки спикеров (проверяет, что диаризация не становится узким
местом на сервере организации).

Инструменты для проверки на реальных данных (папка `server/scripts`):

- **`eval_voices.py`** — проверка диаризации на живых голосах: каждый участник
  наговаривает несколько фраз (`--dir voices/`, папка = человек) или берутся
  аудио «звучаний» из вкладки «Спикеры» (`--samples`). Показывает близости голосов и
  таблицу «порог → сколько профилей получится» — так подбирается
  `SPEAKER_MATCH_THRESHOLD`.
- **`bench_asr.py`** — сравнение всех ASR-моделей по качеству (WER) и скорости
  на синтезированной речи (таблица выше).

## Ограничения (честно)

- Диаризация по коротким репликам (<1 с) неточна — такие реплики приписываются
  последнему говорившему; порог настраивается.
- Каналы распознаются единым смешанным потоком: если два человека говорят
  строго одновременно, в транскрипт попадёт в основном тот, кто громче
  (раздельные каналы справлялись бы лучше ценой двойной нагрузки и дублей эха).
- Подсказки ИИ — демо-режим: на локальной LLM с 8 ГБ RAM они редкие (мелкая модель
  делит память с ASR); с внешним API отвечают заметно быстрее.
- Протокол длинной встречи (>~40 мин разговора) строится по сокращённому
  транскрипту (начало + конец) из-за контекста локальной модели.
