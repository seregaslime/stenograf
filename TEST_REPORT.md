# Отчёт о тестировании — Стенограф

Автоматические тесты покрывают проект на четырёх уровнях (юнит → функциональные →
интеграционные → e2e) плюс нагрузочный. Всего **135 автоматических тестов**
(120 сервер + 15 клиент), покрытие серверного кода — **75%** на быстром наборе
(модельный конвейер добирается интеграционными и e2e). Ручной чек-лист для того,
что автоматизировать нельзя (реальный микрофон, эхо колонок, упакованное
приложение), — в [TESTING.md](TESTING.md).

## Пирамида и числа

| Уровень | Что проверяет | Тестов | Где |
|---|---|---:|---|
| **Юнит** (сервер) | одна функция/класс в изоляции, зависимости замоканы | 88 | `server/tests/test_{crud,vad,summary_format,ollama_client,transcriber_junk,config,hints,live_session,registry,mixer,llm_provider}.py` |
| **Функциональные** | REST-фичи через публичный API против требований (чёрный ящик) | 15 | `server/tests/test_api.py` |
| **Интеграционные** | модули вместе на реальных зависимостях (миграции БД, реальная ECAPA) | 3 + 3 | `server/tests/test_migrations.py`, `test_diarization_integration.py` |
| **E2E** | система целиком: живой сервер + WebSocket, встреча от аудио до REST | 10 | `server/tests/test_e2e_live.py` |
| **Нагрузочные** | N параллельных встреч, задержка и память | 1 + скрипт | `server/tests/test_load_smoke.py`, `server/scripts/loadtest.py` |
| **Юнит** (клиент) | чистая логика фронтенда (Vitest + jsdom) | 15 | `client/src/**/*.test.ts` |

## Как запускать

```bash
# Сервер — быстрый набор (юнит + функциональные + миграции) с покрытием
cd server && .venv/bin/python -m pytest --cov=app --cov-report=term-missing

# Медленные уровни — по маркерам (реальные модели / живой сервер / нагрузка)
.venv/bin/python -m pytest -m integration      # реальная ECAPA на синтезе голосов
.venv/bin/python -m pytest -m e2e              # живой uvicorn + WebSocket, встречи целиком
.venv/bin/python -m pytest -m load             # дымовой нагрузочный (2 встречи)
.venv/bin/python scripts/loadtest.py --meetings 5 --seconds 30   # полноценная нагрузка

# Клиент — Vitest
cd client && npm run test          # прогон
npm run test:cov                   # с покрытием
```

По умолчанию `pytest` гоняет только быстрый набор — `integration`, `e2e` и `load`
исключены в `pytest.ini` (нужны модели/живой сервер).

## Уровни подробно

### Юнит (сервер) — изоляция
Быстрые (< 2 c на весь набор), без сети и без загрузки моделей. Фикстуры `cfg` и
`db_session` (in-memory SQLite) из `conftest.py`; HTTP-клиенты мокаются
`httpx.MockTransport`. Покрывают: операции с БД (`crud`), буферную нарезку VAD
(`_cut`/`_trim_buffer`), форматирование транскрипта (`build_transcript`), клиентов
LLM (Ollama и OpenAI-совместимый — успех и ошибки), фильтр галлюцинаций ASR,
конфиг и персист выбора движка, движок подсказок (адаптивный триггер, дедуп,
бэкофф), правила диаризации и микшер каналов.

### Функциональные — фича через API против требований
`test_api.py` поднимает приложение через FastAPI `TestClient` (in-process, чёрный
ящик) на временной БД и проверяет соответствие требованию: форму ответа и коды
ошибок для `/api/health`, `/api/asr`, `/api/llm` (вкл. отказ при непровайдере и
ненастроенном API), `/api/meetings` (список/деталь/удаление/резюме/экспорт **md и
txt**), `/api/speakers` (переименование, запрет удаления «Вы», merge-гард).

### Интеграционные — модули вместе на реальных зависимостях
`test_migrations.py` — миграции схемы БД на реальном файле SQLite: старая схема →
миграция → апгрейд без потери данных (AUTOINCREMENT, перенос центроидов в
`voiceprints`, слияние аудио-образцов). `test_diarization_integration.py` (`-m
integration`) — реальная модель ECAPA на синтезированных голосах macOS: intra >
inter похожесть, разделение трёх голосов, подавление эха колонок.

### E2E — система целиком
`test_e2e_live.py` (`-m e2e`) поднимает настоящий uvicorn на временной БД и
прогоняет 10 сценариев целиком через WebSocket: эхо без дублей, энролл владельца и
узнавание между встречами, несколько голосов + короткая реплика, гость → новый
профиль, тишина, разрез длинного монолога, обрыв связи, ошибка резюме при
недоступном Ollama, REST-операции, переключение ASR-движка.

### Нагрузочные — производительность и память
`scripts/loadtest.py` поднимает свой сервер и гоняет N параллельных встреч,
синтезируя речь через `say`. Мерит сквозную задержку встречи (p50/p95), число
сегментов, **пиковый RSS сервера** и ошибки. Узкое место — глобальный лок ASR
(`Transcriber._infer_lock`): все встречи ждут один транскрайбер.

### Юнит (клиент) — Vitest + jsdom
Чистая логика фронтенда без браузера: `store` (адрес сервера, префикс настроек,
режим отладки), `formatTime`, кодирование бинарного аудио-кадра `sendAudio` (байт
канала + PCM), обработка ошибок `rest.request`, распознавание loopback-устройств.
UI-страницы (`LivePage`, `SettingsPage`…) не покрываются юнитами — они проверяются
`tsc --noEmit`, `vite build` и ручным чек-листом.

## Покрытие

**Сервер — 75%** (быстрый набор; `pytest --cov`). Полностью покрыты `config`,
`db/crud`, `db/models`, `llm/router`, `llm/prompts` (100%); высоко — `db/database`
98%, `llm/ollama_client` 95%, `audio/mixer` 94%, `diarization/registry` 94%,
`llm/openai_client` 81%. Ниже показатели у модельного/конвейерного кода
(`asr/transcriber` 51%, `audio/vad` 43%, `ws` 49%, `llm/summary` 48%) — эти пути
исполняются интеграционными и e2e-тестами, которые в замер покрытия не входят.

**Клиент** — по тестируемым модулям: `store.ts` 88%, `api/rest.ts` 57%,
`api/live.ts` 42% (покрыт критичный `sendAudio`); UI-страницы вне юнит-скоупа.

## Нагрузочный прогон (замер)

`loadtest.py --meetings 3 --seconds 12` (движок GigaAM v3, Mac M3):

| Метрика | Значение |
|---|---|
| Встреч одновременно | 3 × 12 c речи |
| Общее время (wall) | 2.7 c |
| Сквозная встреча p50 / p95 / max | 1.8 / 1.8 / 2.3 c |
| Распознано сегментов | 3 |
| Пиковый RSS сервера | ≈ 1.2 ГБ |
| Ошибок | 0 |

GigaAM обрабатывает речь быстрее реального времени (12 c аудио за ~2 c), память
далеко в рамках 8 ГБ. При росте числа встреч задержка увеличивается линейно
из-за сериализации на локе ASR — это и есть ожидаемое узкое место.
