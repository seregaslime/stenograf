# Правила работы над «Стенографом»

Десктоп-приложение для транскрипции встреч: клиент Electron + React + TypeScript
(Vite), сервер Python + FastAPI. Практика в ОЦРВ, работу принимает куратор.

Архитектуру здесь не описываем — она в [README.md](README.md) и в графе
зависимостей (см. «Инструменты»). Тут только то, что иначе будет сделано не так.

## Как запускать

```bash
sh server/run.sh                  # сервер: uvicorn на 127.0.0.1:8765, --reload
cd client && npm run dev          # клиент
./start.sh                        # всё сразу: Ollama + сервер + приложение
```

Тесты:

```bash
cd server && .venv/bin/python -m pytest tests -q      # быстрый набор
cd server && .venv/bin/python -m pytest -m e2e        # маркеры: integration, e2e, load
cd client && npm test && npm run typecheck
```

Правки интерфейса проверять самому в браузерной превью (конфигурация `client-web`
в [.claude/launch.json](.claude/launch.json)): открыть страницу, посмотреть
консоль и вёрстку, показать снимок. Не просить Сергея «проверь, пожалуйста» —
проверка это моя часть работы.

## Язык и стиль

- Комментарии, сообщения коммитов, тексты интерфейса и ответы в чат — по-русски.
- **Комментарий объясняет «почему», а не «что».** Эталон стиля уже в коде:
  [config.py:85](server/app/config.py:85) — там сказано, почему порог именно
  такой и что было не так с прежним значением. Так и продолжать.
- Плотность комментариев брать по соседнему коду, а не по своим привычкам.

## Порядок работы над задачей

1. **Разбор перед крупным.** Если пункт затрагивает конвейер, модели или больше
   двух файлов — сначала скил `razbor` (какую проблему закрываем → что уже есть в
   коде → самое дешёвое решение → что сверх него и зачем → почему может не
   сработать → чем проверим). Разбор заканчивается вопросом Сергею, а не работой.
   Мелкие правки — сразу в работу.
2. **Ветка на пункт плана.** Не коммитить в `main` напрямую: ветка → коммиты →
   пул-реквест. У [tests.yml](.github/workflows/tests.yml) настроен триггер на
   `pull_request` — через PR он наконец начинает работать по назначению, и
   куратору есть что смотреть, кроме готового кода.
   Вливать **обычным merge, не squash**: squash склеит серию аккуратных коммитов
   обратно в один большой — ровно то, за что и было замечание.
3. **`/code-review` перед каждым коммитом.**
4. **Коммит — только по команде Сергея.** Никогда не коммитить и не пушить
   самостоятельно, даже когда всё зелёное.

## Коммиты

Куратор заходит в GitHub между созвонами и читает историю сам. Увидев коммит на
4 тысячи новых строк, он сказал (04.08.2026), что в командной работе так делать
нельзя. Отсюда два следствия: коммит должен объясняться без автора рядом, и
большой пул-реквест получает не более долгое ревью, а худшее — внимание
читающего кончается, и дальше он листает по диагонали.

- Один коммит — одна законченная мысль. Ориентир **до 400 изменённых строк**;
  это ориентир, а не запрет (сгенерированные файлы и переносы не в счёт).
- Крупная задача разбивается на серию коммитов **до** начала работы.
- Заголовок по-русски и содержательный: «Кнопка подсказки больше не забывает
  свои прошлые ответы», а не «fix» и не «wip».

## Тесты

- Любая правка поведения сервера — с тестом в `server/tests/`; клиента — рядом в
  `*.test.ts`.
- **`TESTS.md` и `TEST_REPORT.md` руками не править** — они генерируются:
  `scripts/test_report.py` собирает отчёт, `scripts/test_inventory.py` — каталог.
  Ручная правка затрётся при следующем прогоне.
- Медленные уровни (`integration`, `e2e`, `load`) в обычный прогон не входят —
  они отключены в `pytest.ini` и запускаются маркером.

## Связки, которые легко разорвать молча

Здесь ошибка не ловится ни тестами, ни компилятором — вылезает у пользователя.

- **Схема БД.** Миграции самописные, в `init_db()`
  ([database.py](server/app/db/database.py)). `create_all` создаёт только
  отсутствующие таблицы и **не добавляет колонки в существующие**: добавил поле в
  `models.py` — напиши функцию `_migrate_*` и вызови её в `init_db()`, иначе у
  всех, у кого база уже есть (у Сергея и у куратора), сервер упадёт или потеряет
  данные. Порядок вызовов значим — в существующих миграциях это прямо оговорено в
  комментариях. Новая миграция — с тестом в `test_migrations.py`.

- **Типы клиента.** [types.ts](client/src/types.ts) повторяет серверные DTO
  **вручную**, никакой генерации нет. Поменял форму ответа эндпоинта или событие
  WebSocket — правь `types.ts` в том же коммите. TypeScript тут не поможет: он
  верит объявленному типу, и расхождение вылезет только в рантайме.

- **Новое поле конфига.** Настройки читаются с префиксом `STENOGRAF_`
  ([config.py:23](server/app/config.py:23)). Добавил поле в `Settings` — обнови
  `server/.env.example` и раздел «Конфигурация сервера» в README.

- **Подобранные эмпирикой числа не трогать на глаз.** Порог диаризации 0.35
  ([config.py:57](server/app/config.py:57)), пороги подсказок, параметры VAD —
  подбирались замерами. Менять только с прогоном `scripts/eval_voices.py` или
  `scripts/bench_asr.py` и с новым числом в описании изменения.

## Меньше кода

Перед тем как писать код, остановиться на первой подходящей ступени: нужно ли это
вообще → нет ли уже в кодовой базе → нет ли в стандартной библиотеке → нет ли в
платформе → нет ли в уже установленной зависимости → нельзя ли одной строкой →
и только потом писать минимум. Развёрнутая версия — в скиле `ponytail`.

Лениться нельзя в: понимании задачи, валидации на границах доверия, обработке
ошибок с потерей данных, безопасности и во всём, что запрошено явно.

У клиента всего четыре рантайм-зависимости (`react`, `react-dom`, `marked`,
`electron-audio-loopback`). Пятая должна себя окупать.

## Границы

- `server/.env` не трогать и не читать наружу: там ключ внешнего API, файл в
  `.gitignore`. **Ключ** на клиент не уходит никогда — наружу отдаётся только
  флаг `api_configured` ([main.py:216](server/app/main.py:216)). **Адрес API не
  секрет**: клиент сам задаёт его в настройках, и `/api/llm` его возвращает —
  прятать адрес в сообщениях об ошибках не нужно.
- Не менять выбранного провайдера LLM и модели без просьбы.
- Аудио встреч наружу не отправлять: политика безопасности данных организации.

## Грабли проекта

- **venv через uv:** в `server/.venv` нет `pip`. Ставить только
  `uv pip install --python .venv/bin/python -r requirements.txt`.
- **qwen3 в Ollama:** не отключать `think` (иначе рассуждения лезут в текст
  ответа) и не задавать `num_predict` (мысли съедают лимит — ответ приходит
  пустым).
- **vite слушает только IPv6** — запускать с `--host 127.0.0.1`.
- **Резюме через внешний API:** брать не-reasoning модель (`openai/gpt-oss-120b`,
  `llama-3.3-70b-versatile`). Рассуждающие вываливают ход мыслей прямо в текст.
- **Системный звук в dev-режиме:** macOS привязывает разрешение к «ответственному
  процессу». Сергей запускает `npm run dev` из терминала VS Code, поэтому доступ
  выдаётся **Visual Studio Code**, а не Electron.
- **Сеть нестабильна** (внешние API только через VPN): большие загрузки — с
  повторами, у сетевых ошибок должен быть внятный текст, а не таймаут в никуда.
- Ollama работает без VPN — надёжный дефолт для демонстраций.

## Инструменты

- **graphify** — граф зависимостей проекта. Перед поиском по структуре («кто
  вызывает X», «что сломается, если тронуть Y») спрашивать граф, а не грепать
  вслепую. Бинарник не на PATH: `~/.local/bin/graphify`.

  ```bash
  ~/.local/bin/graphify explain "SpeakerRegistry"
  ~/.local/bin/graphify god-nodes --top 10
  ```

  Граф пересобирается сам после каждого коммита (git-хук, в фоне). Вручную —
  `graphify update .`. Полезен для структуры; поиск конкретного значения в коде
  (например, где зашито `device="cpu"`) он не заменяет — там нужен grep.

- **Скилы проекта** в `.claude/skills/`: `razbor`, `ponytail`, `sozvon`
  (подготовка к созвону с куратором), `ui-ux-pro-max` (база палитр, шрифтов и
  правил доступности), `design-system`, `slides`.

- **Ревью:** `/code-review` перед коммитом, `/security-review` периодически —
  в проекте есть ключ внешнего API и приём аудио.
