# Подготовка к созвону

Куратор заходит в GitHub между созвонами и читает историю сам. На созвоне он
сверяет свой чеклист. Задача — прийти с готовым ответом «что сделано и чем это
доказывается», а не вспоминать на ходу.

Реальная проблема, ради которой это делается: работа бывает сделана, а зачёта за
неё нет, потому что куратор о ней не узнал. 04.08.2026 выяснилось, что несколько
пунктов его чеклиста были закрыты давно — просто об этом никто не сказал.

## Что собрать

**1. Что изменилось с прошлого раза.** Взять коммиты с даты прошлого созвона:

```bash
git log --since="ДАТА" --oneline --stat
```

Пересказать **человеческим языком и по задачам**, а не списком коммитов. Куратора
не интересует «правка ws.py» — его интересует «подсказки перестали повторяться».

**2. Чем это доказывается.** У каждого пункта — конкретная опора: файл со
строкой, номер теста, эндпоинт, который можно дёрнуть, число в отчёте. Пункт без
опоры на созвоне не заявлять: «вроде сделали» хуже, чем «не делали».

**3. Свежие числа.** Сгенерированные отчёты обновить, а не пересказывать старые:

```bash
cd server && .venv/bin/python scripts/test_report.py    # TEST_REPORT.md
cd server && .venv/bin/python scripts/test_inventory.py # TESTS.md
```

Полный прогон с медленными уровнями — `test_report.py --all`, если есть время.
Числа брать из свежего прогона; если прогнать не удалось — так и сказать, а не
называть прошлые.

**4. Приложение живое.** Запустить и убедиться, что оно работает: сервер
поднимается, клиент открывается, встреча начинается и распознаёт. Сломанная
демонстрация на созвоне обнуляет всё остальное.

**5. Что осталось и что мешает.** Честный список незакрытого. Если что-то
буксует — назвать причину и что нужно от куратора. Вопрос, заданный вовремя,
выглядит лучше, чем неделя, потраченная не туда.

**6. Вопросы к куратору.** Собрать накопившиеся развилки, где его решение
экономит время. Спрашивать про них на созвоне, а не гадать после.

## Что отдать Сергею

Короткая сводка, которую можно прочитать вслух или скинуть текстом:

- сделано с прошлого раза — по задачам, с доказательством у каждой;
- какие пункты чеклиста этим закрываются (и какие закрыты были раньше, но
  куратор мог не заметить);
- свежие числа по тестам и покрытию;
- что осталось, что мешает;
- вопросы.

Отдельной строкой — **что куратор увидит в GitHub**, если зайдёт: сколько
коммитов, какие пул-реквесты открыты, зелёный ли CI. Он туда заходит, и лучше
знать заранее, что он там найдёт.

## Правила

- **Не приписывать себе несделанное.** Соблазн засчитать «почти готово» велик, а
  цена высока: куратор проверяет код. Одна приписка дороже трёх честных «не
  успел».
- **Не пересказывать git log.** Если пункт не переводится на человеческий язык —
  значит, непонятно, зачем он делался, и это сам по себе повод для разговора.
- Проверять утверждения по коду, а не по памяти — своей или Сергея.
